1. Individual App Architecture Analysis

Yelp

Search + AI Assistant SOA / Microservices

Infrastructure

  • Architecture: Service-Oriented Architecture (SOA) since 2011. 150+ production microservices by 2014, now significantly more. Runs on custom PaaS called "PaaSTA" (open-source), originally on Apache Mesos, now migrated to Kubernetes.
  • Language: Primarily Python (Pyramid web framework + gevent for async). Docker containerized.
  • NOT serverless. Traditional containerized microservices on Kubernetes. No edge functions.

Yelp Assistant (AI Feature) -- Architecture Deep Dive

  • Pattern: Multi-stage RAG (Retrieval-Augmented Generation) -- NOT a monolithic chatbot.
  • Key components: Interaction Service (WebSocket/SSE), Orchestrator (stateful brain), LLM Gateway (unified model interface), Tool APIs (Search, Reservations, Reviews).
  • Model strategy: Tiered models -- fine-tuned GPT-4.1-nano for classification tasks (Trust & Safety, intent routing, content source selection), GPT-4o reserved only for final answer generation.
  • LLM as Translator: The LLM converts natural language into structured API calls to Yelp's existing search engine. It does NOT try to answer questions from its own knowledge.
  • Intent Classification: Early in pipeline -- simple queries like "Hi" skip the full RAG pipeline entirely.

Data & Caching Strategy

  • Hybrid freshness: Streaming ingestion for high-velocity data (reviews, business attributes) -- updates within 10 minutes. Weekly batch pipeline for slow-moving data (menus, website text).
  • Storage split: Unstructured content (reviews, photos) in Lucene search indices. Structured facts (hours, amenities) in Cassandra (Entity-Attribute-Value layout).
  • Content Fetching API: Abstraction layer in front of all retrieval stores. Parallelizes backend reads. Enforces latency budgets. p95 latency under 100ms.

TripAdvisor

AI Trip Builder RAG + Prompt Engineering

AI Trip Builder Architecture

  • Data foundation: 1+ billion reviews across hotels, restaurants, attractions, activities. Emphasis on "quality first-party data" with high accuracy, taxonomy, and metadata.
  • AI approach: RAG (Retrieval-Augmented Generation) + prompt engineering. Flexible data architecture feeds LLMs structured data, text, images, and documents.
  • Model strategy: Tested many LLM options (open-source and proprietary). Did NOT commit to a single model -- comparative testing strategy. Specific production model not publicly disclosed.
  • Quality control: Human-in-the-loop -- text outputs reviewed for brand compliance and traveler needs validation.
  • Cost management: Design requirements explicitly balance cost, accuracy, and latency as adoption scales.
  • All AI calls are server-side. No client-side LLM inference.

Google Maps

AI Place Summaries Gemini-Powered

AI Summaries Architecture

  • Model: Gemini -- analyzes place information from 300M+ contributors and 250M+ businesses/places.
  • Summary types: Place summaries (100-char short / 400-char long), Review summaries (digest of reviewer sentiment), Area summaries (nearby points of interest + general area description).
  • Processing: NLP to understand queries, data analysis scanning descriptions/photos/reviews/ratings, then recommendation generation. All server-side via Places API.
  • Caching: Developers are explicitly PERMITTED to cache Places API responses (including AI summaries). Google likely pre-computes and caches summaries server-side given the 250M+ business scale.
  • Exposed as API: Places API (New) exposes AI summaries as a field -- developers can integrate into their own apps. This is a key pattern: Google does the heavy AI lifting, apps consume via API.

Key Insight for Hype

Google Maps Places API already provides AI-generated place summaries via Gemini. Rather than generating your own AI summaries from scratch, you could consume Google's API and layer your own nightlife-specific intelligence on top. This dramatically reduces AI compute costs.

Airbnb

Event-Driven Personalization Lambda Architecture

User Signals Platform (USP) -- Deep Dive

  • Architecture: Lambda Architecture -- combines real-time streaming with offline batch processing.
  • Core stack: Apache Kafka (event bus) + Apache Flink (stream processing) + KV store (append-only with versioned timestamps).
  • Why Flink over Spark: Flink is natively event-driven (processes each event on arrival). Spark Streaming uses micro-batches which caused unacceptable delays for in-session personalization.
  • Scale: 1M+ events/second, 100+ Flink jobs, 70K queries/second served to downstream services.
  • Signal types: Simple (direct Kafka-to-signal mapping) and Join Signals (real-time stateful joins using RocksDB). Defined via YAML configuration.
  • Resilience: Hot standby Task Managers pre-provisioned for immediate failover (seconds, not minutes).

AI Strategy (2025-2026)

  • Natural language search: Conversational AI powered by NLP -- "cozy apartment for two in Lisbon with ocean view" returns relevant results.
  • Vision: AI-native app that "knows you" -- helps guests plan trips, hosts run businesses, company operate efficiently.
  • Leadership: Ahmad Al-Dahle (ex-Meta, led Llama development) hired as top tech exec in early 2026.
  • Research areas: NLP, optimization, measurement science. Active at KDD and CIKM conferences.

Fever

Experience Discovery Behavioral Data Mining

Personalization Approach

  • Proprietary algorithm: Learns from user behavior to create personalized event/experience recommendations. Goal: "act like a best friend" showing events you would not want to miss.
  • Demand prediction: Uses anonymized behavioral data-mining to algorithmically predict untapped demand for events that do not yet exist. This is their core competitive advantage.
  • Secret Media Network: 200+ hyper-local digital channels (e.g., "Secret London") with 300M+ monthly interactions. This content network feeds behavioral signals back into recommendations.
  • Architecture details: Limited public information. Responsive web + native iOS/Android apps. No engineering blog or public technical disclosures found.

Key Insight for Hype

Fever's competitive moat is NOT their tech stack -- it is their behavioral data flywheel. Content drives engagement, engagement produces signals, signals improve recommendations, better recommendations drive more engagement. The architecture is secondary to the data strategy.

Discovery & Personalization

3. Universal Patterns Across All Apps

Pattern 1: ALL AI Calls Are Server-Side

Every single app studied runs AI inference server-side. No app sends LLM API keys to the client or makes AI calls from the frontend. The reasons are consistent:

  • API key security (never expose OpenAI/Gemini keys to client)
  • Cost control (server can enforce rate limits, caching, and early stopping)
  • Quality control (server can validate, filter, and post-process AI outputs before sending to client)
  • Latency optimization (server can parallelize retrieval + AI calls, stream results via SSE)

Pattern 2: RAG Over Fine-Tuning

Both Yelp and TripAdvisor use RAG rather than fine-tuning models on their data. The pattern is:

  • Keep your proprietary data in your own search indices / databases
  • Use the LLM as a translator (natural language to structured queries) and generator (structured data to natural language answers)
  • Never try to teach the LLM your facts -- retrieve them at query time

This is directly applicable to a city discovery app: store venue/event data in Supabase, use the LLM to translate user queries and generate responses.

Pattern 3: Tiered Model Strategy

Yelp's approach is the clearest example: cheap/fast models for classification and routing, expensive models only for final generation. This controls costs while maintaining quality.

  • Cheap tier (GPT-4.1-nano or similar): Intent classification, safety checks, content source selection, keyword generation
  • Expensive tier (GPT-4o or similar): Only for final answer generation where nuance matters
  • No model tier: Simple queries bypass the AI pipeline entirely (intent routing)

Pattern 4: NO Successful App Uses Edge Functions as Primary Backend

Every app at scale uses traditional containerized microservices (Kubernetes) or managed services. The pattern is clear:

  • Yelp: Kubernetes (PaaSTA)
  • Airbnb: Kubernetes + Kafka + Flink
  • DICE: Kubernetes (Helm + custom operator)
  • Wanderlog: Node.js/Express (traditional server)
  • Google Maps: Custom Google infrastructure

However, these are all mature companies at massive scale. This does NOT mean edge functions are wrong for a startup.

Pattern 5: Event-Driven for Real-Time Personalization

Airbnb's architecture is the gold standard: every user interaction is an event processed in real-time to update personalization signals. The pattern:

  • User action generates event (click, search, view, bookmark)
  • Event flows through message bus (Kafka)
  • Stream processor (Flink) transforms events into signals
  • Signals stored in fast KV store for query-time personalization

For a Supabase-based app, this maps to: Supabase Realtime (event bus) + Edge Functions (lightweight processing) + Supabase DB (signal storage).

4. Verdict: Is Supabase Edge Functions Viable for Hype?

Yes -- with important caveats

Supabase Edge Functions is a reasonable architecture for an early-stage city discovery app. No successful competitor started with the architecture they have today. The key is knowing when you will outgrow it.

What Edge Functions Are Good For (Your Use Case)

Ideal Edge Function Tasks

  • AI API proxy (call OpenAI/Gemini server-side, stream results to client via SSE)
  • Intent classification and routing (cheap model calls)
  • Geolocation-based content serving
  • Auth token validation and user context injection
  • Webhook handlers for event/venue data updates
  • A/B testing and feature flags
  • Rate limiting AI calls per user

NOT Suitable for Edge Functions

  • Complex multi-step RAG pipelines (need persistent orchestration state)
  • ML model training or heavy inference
  • Transactional writes (payment processing)
  • Long-running background jobs (data ingestion pipelines)
  • Stateful event stream processing (Kafka/Flink equivalent)
  • Large file processing

Recommended Architecture for Hype (Startup Phase)

Client (React Native) | |-- Auth requests ---------> Supabase Auth | |-- Data queries ----------> Supabase PostgREST (direct DB access) | |-- AI requests -----------> Supabase Edge Function (AI Proxy) | | | |-- Intent classify (cheap model) | |-- Route to: search / recommend / chat | |-- Retrieve context from Supabase DB | |-- Call OpenAI/Gemini (expensive model) | |-- Stream response via SSE | |-- Cache result in Supabase DB | |-- Real-time updates -----> Supabase Realtime (WebSocket) | | | |-- Event availability changes | |-- New events near user | |-- Friend activity updates | |-- Place summaries -------> Google Maps Places API (Gemini summaries) (consume, don't rebuild)

5. Actionable Recommendations for Hype

Steal These Patterns

  1. Yelp's "LLM as Translator" pattern: Do not feed raw venue data to the LLM. Have the LLM translate user intent into structured Supabase queries, retrieve results, then have the LLM format the response. This keeps costs low and results accurate.
  2. Yelp's tiered model strategy: Use a cheap model (GPT-4.1-nano / GPT-4o-mini) for intent classification and a premium model only for final generation. Most requests should never hit the expensive model.
  3. Google Maps' pre-computed summaries: Consume Google Places API for venue descriptions instead of generating your own. Layer nightlife-specific context (vibe, crowd, music) on top from your own data.
  4. Fever's behavioral data flywheel: Start collecting user interaction signals from day one. Every tap, view, bookmark, and share is a signal. Store these in Supabase and use them for recommendations even before you have ML models -- simple collaborative filtering works.
  5. RA's music sync integration: Spotify/Apple Music artist sync for nightlife personalization is proven and loved by users. This gives you strong preference signals without asking users to fill out profiles.
  6. Airbnb's SSE streaming: Stream AI responses token-by-token to the client. This makes 3-second AI responses feel instant because the user sees text appearing immediately.

Avoid These Anti-Patterns

  • Do NOT build a monolithic AI chatbot. Yelp explicitly warns against this -- use intent routing + specialized tools.
  • Do NOT fine-tune models on your data at this stage. RAG is cheaper, more flexible, and your data changes constantly (events are ephemeral).
  • Do NOT make AI calls from the client. Zero successful apps do this. Always proxy through your backend/edge functions.
  • Do NOT try to generate venue descriptions from scratch. Google already does this with Gemini at a quality level you cannot match. Augment, do not replace.
  • Do NOT over-engineer the real-time system. You do not need Kafka+Flink at startup scale. Supabase Realtime + Edge Functions can handle early-stage event-driven features.

Bottom Line

Supabase Edge Functions is a valid starting architecture. Every competitor started simpler than where they are today. The critical insight from this research is that architecture matters less than data strategy at the startup phase. Fever's moat is behavioral data, not infrastructure. Yelp's AI advantage is their billion reviews, not their Kubernetes cluster. Google Maps' AI summaries work because of 300M contributors, not because of Gemini.

Your priority order should be: (1) Collect user behavior signals, (2) Build a great recommendation feedback loop, (3) Use AI to enhance -- not replace -- the discovery experience, (4) Worry about infrastructure scale when you have scale problems.
